# v0.5.1 verification — 31 October 2026

Status: application repairs implemented; the full human room-acoustic and latency acceptance gate remains open. No roadmap completion marker was changed. This release does not train Qwen or promise that every future answer will be correct.

See the [31 October reliability gate](reliability-gate-2026-10-31.md) for the subsequent 27-case real-Qwen/SQLite acceptance run, live wake-boundary repair, current regression totals and room-test results. The historical timings below remain observations from the earlier verification run.

## Reproduced defects and repairs

- Native microphone startup failed with `-10875`: voice-processing input/output client formats now match.
- A seven-channel input had measurable speech but implicit mono conversion produced zero: channel-zero mapping now preserves the signal. The installed helper's microphone-free conversion self-test passes.
- Small helper commands were buffered by a pipe read: immediate reads now allow readiness and cancellation to proceed.
- Wake recognition could finalize during silence and be discarded by a same-frame speech gate: recent sustained acoustic evidence now validates the delayed lexical result. The standalone fixture changed from no wake to detection at 1.34 seconds. Negative speech fixtures remained negative.
- Browser native requests used an incorrect fetch receiver; older segment events could overwrite newer playback. Both have regressions.
- Disconnect, preview/capture switching, device changes and cancellation could leave mismatched owners. Generation-bound cleanup, release acknowledgement, bounded queues and request-wide cancellation now fence late work.
- Approved-memory recall missed real spoken request framing, including `Just tell me what my favorite color is.` Recall now handles polite/greeting prefixes and complete multi-field recall clauses, supplies only requested fields, and retains current-correction, quotation and fictional-context protections. Requests to recall a fact are distinguished from requests to create a reminder.
- Unsupported capability claims and unrequested repetition have application-level boundaries and a labelled manual retry. Qwen's general factual and instruction-following reliability remains limited.

## Validation

All **131 JavaScript and 288 Python tests pass**. The suites cover PCM encoding, invalid uploads, silence, permission/cancellation races, worker deadlines/restarts, competing owners, stale speech events, retention, memory approval/correction and repetition. TypeScript and the production build pass. Next.js is pinned to 16.4.3; the final npm audit reports zero vulnerabilities.

Real installed native IPC and silent voice preparation pass without opening a microphone. Nicky playback, captions, completion and Stop voice were verified in the browser. Desktop (1440 px) and mobile (390 px) had no horizontal overflow; keyboard focus and Still view were checked. Still view is not a substitute for a physical OS reduced-motion preference check.

The local signal pipeline was also exercised with synthetic speech using real Vosk, Silero and the resident Whisper service, followed by a real Qwen request: standalone/combined wake questions, Indian English synthesis, ordinary-speech interruption, silence and a steady-tone negative. These fixtures do not establish human room echo rejection. Word spacing such as `WebWorker` versus `web worker` is allowed in fixture assertions; identifiers are not rewritten.

All seven integration checks passed. After restarting the final backend, the exact saved-colour recall request also passed in the browser, returned its approved fact, played with Nicky and returned to idle with the microphone off. The browser reported first text in 0.2 seconds and first playback at 773 ms for this application-owned recall; these timings exclude voice input and do not describe general Qwen answers. The final browser warning/error log was empty.

## Measured performance and held-back changes

- Earlier resident conservative-decoder run: eight short synthetic fixtures, median 1,617 ms, maximum 2,486 ms; fresh-worker readiness 921 ms. This is not an end-to-end human microphone benchmark or a guaranteed cold-start time.
- Browser observation: a typed local reply produced first text at about 0.4 seconds and first audio at about 2.16 seconds from submission. This excludes end detection and transcription.
- Nicky preview: first playback event about 282 ms. Playback events are not laboratory measurements of audible onset.
- Current runs also show slower transcription under concurrent CPU load. The requested speech-to-audio median ≤3.5 seconds and p95 ≤6 seconds have **not been demonstrated**.
- The faster four-thread greedy decoder is **withheld**. GPU identifiers passed, but exact proper-name accuracy failed the release gate in both candidate and baseline. The shipped resident decoder retains two-thread beam-five decoding with fallback. Names still require review/correction.
